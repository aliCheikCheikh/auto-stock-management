== Source of truth

The API contract is maintained in `auto-stock-management/api/openapi.yaml` (OpenAPI 3.1).
Change the contract there and align documentation and server code with it. The notes below record the original API design; they are not a statement of current endpoint coverage or guarantees.

== Specification-driven development and TDD

TDD protects domain rules, such as nonnegative `StockLevel` quantities and currency compatibility in `Money`.
The OpenAPI contract defines integration between backend and frontend.

== Original design principles

=== Explicit versioning

URLs use `/api/v1`. The design calls for a new URL version for incompatible payload changes or removed fields, while additive optional fields or endpoints remain on `v1`.

=== Resource naming

Use plural resources in kebab-case: `/stock-receipts`, `/stock-transfers`, `/stock-levels`, `/stock-movements`, `/sales` and `/products`.
The HTTP verb carries the action rather than paths such as `/createSale` or `/sales/confirm`.

=== Primitive types

* IDs: UUID v4 strings; no exposed Long identifiers.
* Dates: ISO 8601 UTC (`date-time`).
* Money: `{ amount: string, currency: string }`. String amounts preserve `BigDecimal` precision when consumed by JavaScript.

=== Errors

The design uses RFC 7807 `application/problem+json` with `type`, `title`, `status`, `detail` and `instance`, plus:

* `code`: stable machine code such as `STOCK_INSUFFICIENT`, used for frontend localization.
* `errors[]`: field validation errors.
* `traceId`: server-log correlation identifier.

[source,json]
----
{
  "type": "https://api.stock.example.com/errors/stock-insufficient",
  "title": "Insufficient stock",
  "status": 409,
  "detail": "Requested quantity 10, available 4 in shop 3c4d…",
  "code": "STOCK_INSUFFICIENT",
  "traceId": "8f1e2a7b-…"
}
----

=== Planned mutation idempotency

The original proposal accepts `Idempotency-Key: <UUID>` on `POST /stock-receipts`, `POST /sales` and `POST /stock-transfers`, with the same response for repeated keys within 24 hours.
This is a design target intended to prevent duplicate operations after network retries; check the current implementation for actual persistence and expiry behavior.

=== Planned pagination convention

* Query: `?page=0&size=20&sort=field,direction`.
* Response: `{ "content": [...], "page": { page, size, totalElements, totalPages } }`.

Check each operation in OpenAPI for supported parameters and response shapes.

=== Role-based financial visibility

The original design exposes `GET /sales` to both roles and filters financial fields such as `totalAmount` according to the JWT role, using one URL for both roles.

== Original endpoint map

[cols="1,1,1"]
|===
| Endpoint | Use case | Purpose

| `POST /stock-receipts`
| `ReceiveStockUseCase`
| Supplier receipt; create an unknown product if necessary and distribute quantities across locations.

| `POST /sales`
| `SellProductUseCase`
| Sale with automatic allocation, shop floor first.

| `POST /stock-transfers`
| `TransferStockUseCase`
| Transfer between locations in the same shop.

| `GET /products`, `GET /products/{id}`
| Read
| Product catalog.

| `GET /stock-levels`, `GET /products/{id}/stock-levels`
| Read
| Stock by product and location.

| `GET /sales`, `GET /sales/{id}`
| Read
| Sales history.

| `GET /stock-movements`
| Read
| Audit log of receipts, issues and transfers.
|===

== Historical follow-up list

The original design deferred authentication (login, refresh and logout), analytical dashboard projections (`summary`, `daily-revenue`), sale cancellation, and physical inventory adjustments.
This list describes the planning stage, not current implementation status. Consult the current OpenAPI file, source code and README for available functionality.
